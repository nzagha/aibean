## Implemented flows and changed routes

The existing `/login` and `/register` wrappers and branded form classes are preserved. Candidate-only views add `/confirm-email`, `/forgot-password` and `/reset-password`, with field validation, accessible feedback, pending/disabled controls, resend/recovery links and invalid/expired-link handling. The account page uses its existing branded POST sign-out form for password/Supabase modes, so the candidate cannot render Clerk's UserButton without a Clerk provider; a dedicated render regression test verifies both form variants. No unconfigured social, phone or passkey choices are added. Shared application validation requires 8–128 characters, uppercase, a digit and a non-space special character; email length is bounded at 254. Supabase's server-side matching policy remains unverified, and no settings were changed.

Existing POST `/api/auth/login` and `/api/auth/logout` dispatch to exactly one configured identity path. Candidate POST handlers are `/api/auth/register`, `/api/auth/resend`, `/api/auth/recover`, `/api/auth/reset`. GET `/auth/callback` exchanges PKCE codes; `/auth/confirm` supports allowlisted token-hash types only with the initiating browser's signed intent/state/verifier. The alternate template path is unconfigured and not a cross-browser callback. Provider operations require the separate approved-testing gate; without it, handlers return branded unavailable feedback before constructing an Auth client.

The server validates the exact canonical Origin for POST, permits only the framework's loopback URL normalization, bounds streamed forms to 4096 bytes, and rejects unsafe return paths. Responses use private/no-store and callbacks suppress referrers. Credential errors and confirmation/recovery responses minimize enumeration. Candidate attempt budgets are bounded per purpose/address and globally, without trusting forwarded IP headers. Rate-limited logout still removes local cookies, without claiming provider revocation. Incoming request and Server Function logging are disabled in Next development to avoid exposing one-time URLs or arguments. Production proxy/platform logs still require explicit URL-query redaction before real tests/release.

## Candidate isolation and sessions

`src/lib/auth-mode.ts` chooses password, Clerk, disabled or Supabase exclusively; invalid/unknown configuration fails closed. Supabase requires **all** of `AIBEAN_AUTH_MODE=supabase`, `AIBEAN_SUPABASE_RELEASE=candidate`, `AIBEAN_AUTH_ISOLATED=true`, and a loopback-only canonical `NEXT_PUBLIC_APP_URL` in a separate process. Hosted Auth calls additionally require `AIBEAN_SUPABASE_PROVIDER_TEST_APPROVED=true`; it remains unset. A private random `AIBEAN_RECOVERY_SECRET` of 64+ characters is required. No current `.env.local` variable was changed. The current code deliberately accepts no production Supabase release value/domain; cutover needs a reviewed release change.

The existing request-scoped SSR cookie bridge is now wired into the framework proxy **only in the isolated, provider-approved candidate mode**. Verified `getClaims()` refreshes identity; fresh `getUser()` checks confirmed/non-anonymous matching accounts before canonical access. Cookie writes/deletions and SDK cache headers survive redirects. Expired sessions clear only session chunks, preserving pending PKCE verifiers; logout clears project session/flow cookies and app proofs. Failed post-login provisioning abandons newly issued browser state even if provider sign-out fails.

Confirmation/recovery requests issue a signed HttpOnly one-use intent binding flow kind, random callback state, return path and SDK verifier cookies. Callback query flags cannot promote a normal exchange to recovery. Recovery creates a ten-minute proof bound to verified subject/session; ordinary sessions, altered/expired proofs and replay cannot reset a password. Reset consumes the proof, updates the provider-managed password, clears local cookies and requests local provider logout. Normal business access requires a separate eight-hour signed access proof issued only after verified password login or normal confirmation. Removing a recovery marker alone cannot grant business access. Token refresh must retain the verified session ID. A new sign-in is required when this application proof expires.

The limiter/replay registry is bounded **single-process candidate state**, not a distributed production guarantee. A restart loses replay records and simultaneous instances do not share budgets; isolated tests do not establish provider token revocation. Before release, use a shared atomic store and test strict recent-session/step-up requirements for sensitive operations. Supabase access JWTs may remain valid until expiry after logout; fresh account lookup does not prove every session has been revoked. [Supabase sign-out guidance](https://supabase.com/docs/reference/javascript/auth-signout).

## Canonical User and authorization

Verified Supabase UUIDs resolve through the existing private `aibean_private.user_identities` into authoritative `public.users`. A transaction-level advisory lock serializes provisioning per UUID. New ordinary User(id) and mapping insert together using installed defaults, runtime column grants, uniqueness and FKs; failed/colliding mappings roll back without orphans. Existing mapped internal text IDs, capabilities and ownership are preserved. No email merge, TestUsers import, temporary-password reuse or user-metadata capability grant exists. No migration was necessary or created.

`requireUser`, `requireAdmin`, `requireCreator`/`requireApprovedCreator` and `requireVendorCapability`/`requireToolOwner` use canonical identity and current stored capability/Tool ownership. Account saves, Stacks, reviews and claims use actual owner predicates; submitted owner IDs cannot authorize them. Vendor checks include both canonical User and requested Tool. Stack membership now locks the owned Stack and inserts in the same transaction, closing the earlier separated owner-check/write. Public published projections remain available. The restricted Drizzle role is shared server access, so these application predicates remain essential.

Future Vendor editing and other existing placeholder modules were not implemented as unrelated product features. The Tool-scoped authorization contract is tested against installed rows; new sensitive endpoints must apply it. No privileged account or bootstrap was created. Historical ownership migration, privilege step-up and controlled legacy retirement remain separately reviewed release work.
