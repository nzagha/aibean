## First release scope and deliverables

1. **Email/password:** Refactor existing registration/sign-in UI in place to Supabase actions and clear state/error handling. Preserve the current minimum eight characters, uppercase letter, number and special-character policy. Apply consistent server validation, safe redirects, request protections and bounded abuse controls. Avoid account enumeration; log no passwords, tokens or personal records. Keep unrelated social, SMS, passkey and enterprise options hidden until separately configured and validated.
2. **Confirmation/recovery:** Implement allowlisted confirmation/PKCE callback routes, resend handling, password-reset request and recovery-session password update. Test expired/reused/malformed links and invalid return paths. Require confirmed identity before protected business access. Validate actual mail delivery and redirect configuration before making those flows available. [Supabase password-based Auth guidance](https://supabase.com/docs/guides/auth/passwords) defines the provider flows; verify the installed SDK/current docs during implementation.
3. **Canonical identity mapping:** Resolve a server-validated Supabase subject UUID through the private mapping to the existing internal text User ID. Preserve internal IDs and ownership. Provision new ordinary User(id) plus mapping atomically/idempotently using the existing restricted Drizzle contract; DB defaults keep Admin/Creator false. Handle concurrency without orphan records, duplicate mappings or account merges. Mapping conflicts fail closed; no email-only merge or TestUsers import. Any legacy linkage needs proven legacy ownership or explicit audited operator review. Do not migrate the shared temporary password.
4. **Sessions:** Connect the already prepared request/response cookie bridge to Next.js proxy only at the approved release boundary. Verify server identity instead of trusting raw cookie/session contents; preserve refreshed/cleared cookie chunks and no-store headers across redirects. Test refresh, expiration, logout and revoked-session behavior. Use stronger current-session/reauthentication checks on sensitive actions. [Supabase SSR guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs) distinguishes verified claims from session-cookie reads; follow the installed Next.js guides before editing proxy/route behavior.
5. **Authorization:** Load authoritative application capabilities for the mapped User on the server. Public browsing remains allowed. Admin, approved Creator and Tool-scoped Vendor checks must use stored capabilities/ownership, never signup metadata, paid status or arbitrary client IDs. Preserve exactly one approved owner per Tool and independent payment/editorial decisions. Revalidate ownership in actions/routes/transactions, since the shared Drizzle login does not inherit the visitor JWT and its RLS policies do not isolate visitors by themselves. Replace the Clerk-prefix admin bootstrap through an explicitly reviewed operator path; runtime cannot elevate Admin/Creator flags.
6. **Controlled retirement:** Build/test the candidate while the existing provider remains the sole active website identity path. Present a concrete release/cutover diff after acceptance. A separately authorized coordinated cutover changes the active mode, invalidates legacy cookies, and removes obsolete Clerk/custom-auth routes, dependencies and secrets after continuity checks. Never run two active identity systems or return normal runtime traffic to postgres. Preserve unresolved historical ownership rather than merging or deleting it.
