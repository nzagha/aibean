# Additive recovery coverage design v4.0 — Admin Review and Operations

**DESIGN ONLY. No hosted backup, export or restoration is authorized or executed.** The original successful TestUsers archive and verified v3 foundation archive remain preserved. Frozen v3 scope, executor, manifest and historical artifacts are unchanged. No private configuration is edited.

The existing v3 checkpoint restores eighteen foundation tables and two sequences, including TestUsers, private identity/security structures and the original Drizzle history. It cannot restore the six Admin Review relations installed under Authorization 5. Applying Operations v2 would add five more relations, leaving eleven relations outside v3. The ledger hashes are reproducible package identifiers; their original installation timestamps and future review/billing rows cannot be recovered from v3 alone. A rollback of a still-uncommitted installation differs from restoring a committed package; no automatic reset or reinstall is permitted.

| Checkpoint | Exact scoped count | Recommendation |
| --- | --- | --- |
| Existing verified v3 | 18 tables, 2 sequences | Keep immutable; historical foundation recovery only |
| Proposed v4a | 24 tables, 2 sequences | Prepare/native-test/review and separately authorize now, **before the next hosted schema installation**, to protect the already installed review state |
| Proposed v4b | 29 tables, 2 sequences | After a future approved Operations COMMIT and independent PASS, create a separately authorized checkpoint **before any feature writes, accounts or provider tests** |

[Versioned exact object design](../db/recovery/application-coverage-v4-design.json) enumerates both additive scopes, existing sequences and the two new private ledgers. These are proposed inventories, not a runnable replacement for v3 or a claim that Operations is hosted installed. Fresh owner-authorized read-only inventory must establish the exact actual scope before building or executing any new package.

Each new recovery package must freeze its own executor, dependency hashes, archive limits and allowlist. Use a distinct v4 artifact namespace/profile: the immutable v3 helper expects exactly one historical expanded receipt in its original backup directory. Do not add another v3-shaped receipt there or edit the old profile to make discovery pass. Keep original/v3 archive/key bindings and both failed targets unchanged; separately review the new versioned artifact discovery/lifecycle and existing-certificate integration. Preserve full constraints/indexes/sequence ownership, RLS names/roles/qualifications, effective table/column/schema grants, restricted role flags and migration/installation history. Export roles without passwords; never export private keys, credentials or managed Auth/Vault/Storage/Realtime rows. Local empty managed FK prerequisites must be separately reviewed without exporting managed records. Continue bounded native tools, strict project/operator/TLS checks, protected Windows CMS storage, private integrity comparisons, isolated restoration and retained failure artifacts. Do not reuse old export authorizations.

Keep the current pre-activation conditions: both TestUsers rows, zero Auth identities/application Users/mappings and no unexpected review/billing data. Any change requires scope/size/privacy/recovery review, rather than silently widening an allowlist. Original v3 4-MiB/10,000-record bounds are historical; new limits need explicit measured synthetic validation and owner approval.

The Package 2 installer verifies original/v3 archive integrity/decryptability and snapshots predecessor catalogs/ledger/data privately for within-operation continuity. It **does not create a full current-state backup**, claim v3 covers Review, or implement v4 export. The separate verifier independently checks live metadata and protected foundation integrity; it cannot recover original predecessor installation timestamps from v3. Local mechanism readiness is PASS separately from the additional recovery design's unimplemented/unauthorized status. Recommended operator handoff completes v4a first; if the owner instead approves installation relying on v3 plus atomic rollback and preserved immutable predecessor SQL, that limited recovery choice must be explicit in the future authorization.

No feature flags, real accounts, provider subscriptions, live payments or private environment changes follow this design. On a post-COMMIT discrepancy stop for a reviewed forward fix or authorized recovery. Existing backups and stopped failed targets remain untouched.
