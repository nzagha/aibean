## Hosted provider journey

Use two separate browser profiles and cookie jars. Capture only case IDs, pass/fail, HTTP status, private/no-store headers, aggregate counts and timing; disable token-bearing request/response logging. Real passwords, JWTs, cookies, PKCE codes, email links, session IDs and recipient details stay outside screenshots, shell history, repository and public artifacts.

Proposed budget: **two ordinary accounts and at most five triggered messages**: registration for A and B, one confirmation resend for A, and two recovery requests for A. A resend may be suppressed by the provider; record requests and actual receipt separately. No arbitrary-address enumeration sweep or third account is included. Stop at the budget or provider quota; do not change quotas, auto-retry sends or bypass the candidate's limits. Additional delivery retries require a new approval. Schedule within the actual project quotas and candidate limiter; default SMTP cannot be assumed sufficient.

With the verified built-in limit, plan five requests over **at least three separate hourly budget windows**, leaving room for unrelated project mail; account A/B recipient eligibility must be verified first. If custom SMTP is separately approved, use its verified project/provider quotas instead. Run no concurrent send burst. The current 3,600-second JWT lifetime makes a real one-hour refresh observation possible without changing Auth settings.

Compare linked saves/Stacks/reviews/claims before and after refresh, login and password recovery. A real email-change/linking/legacy-merge test is outside this two-account plan and needs its own proof-based authorization; absence of an email parameter plus isolated collision tests must not be described as a completed hosted email-change test.

## Bounded cleanup, retention and failure handling

Cleanup is a distinct approved write phase. Stop both test sessions and disable the isolated provider-test gate first. In one guarded database transaction, compare every manifest fixture's ID, owner and expected final content; abort on drift, unknown references or foreign business attachments. Delete **only** manifest-owned orders, claims, review IDs, save composite keys, Stack memberships and stacks, then fixture tools, in FK-safe order. Verify the exact expected affected-row counts before commit. Use exact allowlisted rate-limit keys only if separate cleanup approval includes them; otherwise retain those bounded counters until normal expiry/maintenance.

Retain the two ordinary Auth accounts, their two application Users/mappings and the canonical CAT-01 prerequisite, with the owner's approved retention period recorded privately. This avoids deleting identity/ownership history under restrictive FKs. Account deletion, mapping/User deletion, Auth identity cleanup, ledger edits, audit-log deletion and any privileged cleanup are **not** implied. Future removal requires a separate reviewed identity/data-lifecycle operation; account deletion alone does not immediately invalidate all issued JWTs.

If a test reveals a leak, unexpected privilege or hosted write outside the manifest, stop further sends/writes and disable the isolated candidate. Keep encrypted recovery artifacts and private evidence; report sanitized affected counts and last successful boundary. Do not run broad deletion, reseed, reset, auto-restore hosted data or erase evidence. A pre-commit fixture/cleanup error rolls back its transaction. If an already committed row changed unexpectedly, present a reviewed forward correction or recovery decision. The expanded archive covers application data, not automatic restoration of managed Auth credentials/sessions/provider settings.

## Future exclusive website cutover

Cutover is separately authorized only after expanded recovery PASS, real provider/delivery/identity tests and implemented cross-user ownership scenarios pass. Blocking decisions and engineering work include:

1. Verify transactional SMTP, sender-domain DNS, password/confirmation policy, approved redirects/templates and actual production HTTPS delivery under `https://aibean.io`. Deployment provider and authoritative DNS/Bluehost record targets require verified selection; invent no deployment address.
2. Replace the candidate Auth limiter and proof replay map with shared atomic controls before multiple instances/restarts. Existing business-action PostgreSQL rate limits are durable; they do not make the candidate's Auth limiter/replay map shared. Test replay and bounds across independent processes.
3. Define copied-token/session revocation guarantees and sensitive-action recent reauthentication/AAL2 enforcement. Fresh `getUser` plus the signed access proof does not establish immediate session revocation. Current local sign-out and eight-hour access proof have explicit limitations. [Supabase sign-out semantics](https://supabase.com/docs/reference/javascript/auth-signout).
4. Inventory historical password/Clerk internal IDs and ownership privately. Map a claimant only after verified legacy ownership or audited operator proof; equal email alone cannot merge accounts. Preserve unresolved historical records and deny reassignment. No privileged account bootstrap is included.
5. Review a concrete production release configuration/code diff. The current `authMode` rejects non-loopback Supabase activation and accepts only `candidate`; changing `NEXT_PUBLIC_APP_URL` to production alone fails closed. A reviewed production release mode, proof-secret management/rotation, secure cookies, origin/redirect contract and deployment cache behavior must be implemented and tested first.
6. Approve one coordinated exclusive identity boundary: stop legacy sign-in issuance; activate only validated Supabase; invalidate/clear legacy password/Clerk cookies and ensure legacy auth routes cannot issue accepted sessions. Retire dependencies/configuration after compatibility checks, with no concurrent active providers in one release.
7. Use public browse/protected-action smoke tests and monitored sanitized errors on the selected HTTPS host. Maintain a disable-auth/write incident path. Do not silently re-enable legacy identity against newly provisioned Supabase accounts as a rollback. Any legacy return needs an explicit reviewed continuity decision; preserve database/mapping history and recovery artifacts.
